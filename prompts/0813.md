We are designing the graph library of CSLib. Your task is **architecture and API design, not implementation**.

Approach this as a **TCS researcher who wants to formalize graph algorithms in Lean**, rather than primarily as a pure graph theorist or as someone trying to reproduce Mathlib.

The eventual goal is to have a coherent, usable graph package on top of which we can formalize graph algorithms such as BFS/DFS, shortest paths, SCCs, MST, flows/cuts, connectivity algorithms, dynamic graph operations, etc.

For this task, do **not** start filling in Lean files. Instead, inspect the relevant code and produce a proposed initial architecture for GraphLib, including the expected directory/file structure and the main definitions/APIs that each file should eventually contain. Proposed files and definitions are allowed to not exist yet; they should serve as the construction plan for the next stage.

Output your results in Reports folder.

## Three sources of evidence

Your design should be based on three main inputs.

### 1. Our desired end result

This is the primary objective.

We want a graph package aimed at theoretical computer science and graph algorithms. Important use cases include:

* directed and undirected graphs;
* simple graphs as common algorithmic objects;
* general/multigraphs when explicit edge identity or parallel edges matter;
* vertex/edge deletion;
* induced and spanning subgraphs;
* reversing directed edges or paths;
* contractions;
* vertex splitting;
* graph relabeling;
* path/walk/cycle manipulation;
* weighted graphs;
* capacities and costs;
* reachability and connectivity;
* later formalizations of BFS, SCC, shortest paths, MST, maxflow/mincut, dynamic algorithms, etc.

The mathematical graph API should make such operations reasonably close to how TCS researchers write them on paper and should avoid unnecessary coercion/subtype/cast overhead where possible.

Do not optimize the architecture for one existing theorem or one current module. Think about the package we would like to use for several years.

### 2. Mathlib's graph development

Treat Mathlib as **important prior art, not as the specification**.

Inspect the current Mathlib graph-related development, especially foundational material such as:

* `Mathlib/Combinatorics/SimpleGraph/...`
* `Mathlib/Combinatorics/Graph/...`
* `Mathlib/Combinatorics/Digraph/...`
* walk/path/cycle infrastructure;
* degree/neighborhood/incidence APIs;
* subgraphs and graph operations;
* maps/relabeling;
* finite graph APIs;
* connectivity and acyclicity infrastructure;
* standard graph constructors;
* other foundational files that are clearly relevant.

Also inspect relevant ongoing GraphLike / incidence / unified-walk work if useful for understanding the current design discussion.

However:

* distinguish **merged/stable Mathlib API** from experimental or draft PRs;
* do not treat an ongoing GraphLike design as settled;
* do not mechanically conclude that GraphLib needs something merely because Mathlib contains it;
* do not reproduce Mathlib-specific machinery if it exists mainly because of Mathlib's representation choices.

For each important area, try to identify:

1. useful terminology and naming conventions;
2. basic APIs that have clearly become important through downstream use;
3. good abstraction ideas worth adopting;
4. representation-specific machinery that we probably should not copy;
5. known or apparent pain points;
6. current directions in which Mathlib itself is evolving.

A useful principle is:

> reuse Mathlib's accumulated experience without automatically inheriting its technical debt.

Where the mathematical notion is the same, prefer Mathlib-compatible terminology and theorem interfaces unless there is a concrete reason not to.

### 3. The current GraphLib

Inspect the current GraphLib folder carefully.

Use both the actual Lean files and the existing architecture/status report in the repository/context.

Do not treat existing code as sacred. Classify it conceptually into things such as:

* designs already validated by meaningful downstream use;
* reasonable but still provisional designs;
* incomplete scaffolding;
* historical/legacy artifacts that should be deleted or reorganized.

In particular, pay attention to the existing developed chain around

`VertexSeq → SimpleWalk → SimplePath → SimpleCycle → realized-in graph predicates → girth → Moore bound`

and use actual downstream usage as evidence when evaluating whether those abstractions are good.

Likewise, if downstream files currently contain local helper definitions because a basic API is missing, treat that as evidence about what the foundational API should provide.

Do not preserve an existing structure merely because code has already been written.

# Major architecture questions

Explicitly investigate and make recommendations on at least the following.

## A. The four graph notions

We currently have four notions along two axes:

* undirected / directed;
* simple / general-with-edge-identity.

Analyze what role each should play.

Questions include:

* Should `SimpleGraph` and `SimpleDiGraph` be the primary graph types for most graph theory and algorithms?
* How much API should `Graph` and `DiGraph` receive?
* Should we aim for API parity across all four types, or deliberately give some of them a thinner API?
* Which concepts genuinely benefit from abstraction across the four types?
* Which concepts should simply have separate specialized implementations?
* What conversions/forgetful maps between them should be canonical?

Do not assume symmetry among the four types merely because all four exist.

## B. Directory organization

Decide whether the source tree should primarily be organized by:

* graph type,
* mathematical concept/API family,
* or a hybrid.

For example, reason about alternatives of the form

`SimpleGraph/Degree.lean`, `DiGraph/Degree.lean`, ...

versus

`Degree/Simple.lean`, `Degree/Directed.lean`, ...

versus keeping several graph types in one `Degree.lean`.

Base the recommendation on likely long-term maintainability and discoverability, not just present file sizes.

## C. Graph-independent combinatorial objects

Analyze where graph-independent objects such as vertex sequences, walks/path data, cycle data, etc. should live.

In particular, evaluate the current GraphLib strategy of separating combinatorial sequence/path data from the predicate that it is realized in a particular graph.

Compare this with Mathlib's current and proposed walk infrastructure.

## D. Subgraphs and graph transformations

This is particularly important for TCS.

Design the intended APIs for:

* subgraph relation;
* induced subgraphs;
* spanning subgraphs;
* vertex deletion;
* edge deletion;
* graph union/intersection where appropriate;
* relabeling/isomorphism-like transport;
* reverse for directed graphs;
* contraction;
* perhaps underlying/forgetful graph conversions.

Think carefully about what should stay in the same ambient vertex/edge types and what should introduce new types.

## E. Degree / adjacency / incidence / finite APIs

Determine what basic APIs should exist for:

* adjacency;
* edge incidence;
* neighbor sets;
* in/out-neighbors;
* degree;
* in/out-degree;
* incidence sets;
* `Set` and `Finset` views;
* finite vertex/edge enumeration;
* minimum/maximum/average degree if appropriate;
* degree sums / handshake-style results.

Use Mathlib heavily as an API checklist here, but adapt the interface to GraphLib's representation.

## F. Weighted graphs, costs, and capacities

Analyze how weights should interact with graph structures.

In particular, consider whether weights should be:

* part of graph structures;
* separate data indexed by existing vertices/edges;
* wrappers/structures around a graph;
* or some other approach.

Think about:

* edge weights;
* vertex weights;
* capacities;
* costs;
* restricting weights to subgraphs;
* transporting weights through relabeling/reversal;
* distinguishing semantic notions such as weight/cost/capacity while avoiding a combinatorial explosion of graph types.

Do not prematurely impose algebraic assumptions such as nonnegativity or an additive monoid unless they are really representation-level requirements.

## G. Finite mathematical graphs versus executable graph representations

We ultimately care about algorithms, but do not let this task expand into designing the entire verified complexity framework.

Still, identify what the foundational mathematical graph layer should expose so that later executable representations and algorithms can connect to it cleanly.

Distinguish:

* APIs needed now for finite mathematical reasoning;
* possible future executable adjacency-list/array representations;
* bridges that may eventually be required.

Do not solve the entire complexity/accounting framework in this architecture pass.

# Use downstream TCS formalizations as stress tests

Do not judge the architecture only by aesthetic criteria.

Mentally stress-test candidate designs against representative tasks such as:

* state and prove basic reachability facts;
* run BFS conceptually;
* state SCC correctness;
* reverse an `s-t` path in a directed graph;
* delete vertices and edges repeatedly;
* contract a vertex set;
* perform vertex splitting;
* attach capacities and define an `s-t` flow network;
* define weighted path length;
* define an MST instance;
* move a path/weight assignment through relabeling;
* reason about an induced subgraph without excessive casts.

You do not need to implement these algorithms.

Instead, sketch enough expected type signatures / object interactions to determine whether the proposed architecture would make them natural or painful.

If an architecture causes subtype/coercion/cast complications or duplicated APIs, point this out explicitly.

# Important principles

1. **Do not write the implementation in this task.**
   Small pseudo-Lean signatures are allowed only when they clarify an architectural choice.

2. **Do not simply clone Mathlib.**
   Mathlib is prior art and a compatibility target where natural, not the objective.

3. **Do not diverge gratuitously from Mathlib.**
   If the mathematical notion is standard and Mathlib's terminology/API is good, prefer compatibility.

4. **Do not preserve existing GraphLib code merely due to sunk cost.**
   Preserve it when there is evidence that the abstraction is useful.

5. **Downstream use is stronger evidence than isolated aesthetic review.**

6. **Optimize for TCS researchers actually formalizing graph algorithms.**

7. **Prefer simple abstractions over speculative universality.**
   In particular, do not introduce elaborate typeclass hierarchies merely to remove small amounts of duplication unless there are realistic clients.

8. **Do not require all four graph types to expose identical APIs unless this is genuinely useful.**

9. **Keep weights/costs/capacities in mind from the start, but avoid multiplying graph representations unnecessarily.**

10. **Separate architectural decisions from implementation details.**
    The purpose of this task is to leave as few consequential design choices as possible to the later code-generation agent.

The final result should be concrete enough that, after human review, we could hand the resulting design document to one or more agents and say:

> Implement this architecture.

At that point, implementation should mostly be a Lean engineering task rather than another round of graph-library design.
